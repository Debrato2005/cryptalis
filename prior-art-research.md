# Prior-Art Verification: ORM-Layer Per-Subject Crypto-Shredding for Python

## VERDICT

**Is the ORM-layer per-subject crypto-shredding gap real for Python? YES — confirmed.** After checking GitHub, PyPI, GitLab and the specific packages you named, I found no maintained open-source Python project that combines all four of your defining features at the SQLAlchemy `TypeDecorator` / Django custom-`Field` layer: (1) per-data-subject key isolation, (2) key destruction / crypto-shredding, (3) a signed erasure certificate, and (4) integration as a one-line-per-column ORM type. Every Python field-encryption library I found uses a single application-wide key (or at best a per-model/per-callable key) and none performs key destruction or issues erasure proofs. Per-subject crypto-shredding at the ORM type layer exists in .NET (Granit, via EF Core interceptors — explicitly **not** value converters, which matters for your design), and per-subject crypto-shredding exists in Python only in non-ORM forms (a DynamoDB library; a blockchain/event-log PoC). The closest ORM-integrated Python encryption libraries are single-key and unmaintained or lightly maintained. So the specific combination you are building is genuinely unclaimed in the Python ORM ecosystem. The one important qualification is legal, not technical: your central claim ("crypto-shredding satisfies erasure") must be worded carefully — regulators have not endorsed it as legally equivalent to erasure.

## TL;DR

- **The gap is real and buildable.** No maintained Python package delivers per-data-subject crypto-shredding + signed erasure certificate as a SQLAlchemy/Django ORM column type. Existing Python field-encryption libraries (sqlalchemy-utils `EncryptedType`, django-fernet-fields, django-cryptography, django-encrypted-model-fields, django-crypto-fields, django-pgcrypto) are all single-key, and none destroys keys or issues erasure proofs.
- **Your key technical risk is confirmed and solvable — but not with `TypeDecorator` alone.** `bind_processor`/`process_bind_param` receives only the scalar value, never the row or `subject_id`. Granit hit the identical wall in .NET (EF Core value converters can't see the entity ID) and solved it with **save-interceptors**, not converters. In Python, do per-subject key selection in a `before_flush` session event (plus a `contextvars` fast-path), keeping a thin type only for the storage transform.
- **Soften the legal claim.** Cryptographic erase is a recognized *technical* sanitization method (NIST SP 800-88 Rev. 2, §3.2, final 26 Sep 2025), but EU/India regulators have **not** endorsed it as legally equivalent to erasure — the EDPB says "encrypted personal data is still personal data." Claim novelty of the *Python-ORM combination*, not of crypto-shredding or erasure certificates in general.

## Details

### 1. Python ORM field-encryption libraries: per-subject keys? shredding? erasure proof?

None of the established Python libraries support per-subject key isolation, key destruction, or erasure certificates. They are single-key field-encryption libraries.

- **sqlalchemy-utils `EncryptedType` / `StringEncryptedType`** (kvesteri/sqlalchemy-utils). **1,340 GitHub stars per Snyk's package-health page and 332 forks per the repo's Releases page (shown as "Fork 332 · Star 1.3k"); latest release 0.42.1, published 13 December by josecsotomorales.** Still the most-used option. It relies on a single master key defined at model-declaration time (the key can be a callable, so you can swap keys, but there is no per-row/per-subject key management, no destruction, no certificate). It uses AES; a long-standing open issue (#166) documents that the AES engine derives a **static IV** from the SHA-256 of the key — a cryptographic weakness. Maintenance is light: multiple issues remain open on the kvesteri/sqlalchemy-utils Issues page — **#773 (opened Feb 14, 2025), #771 (Jan 27, 2025), #770 (Jan 16, 2025), #769 (Jan 10, 2025), #766 (Dec 10, 2024), all still "Status: Open"** — with limited maintainer response. `EncryptedType` was deprecated in favour of `StringEncryptedType` at v0.36.6. **No per-subject keys, no shredding, no certificate.**
- **django-fernet-fields** (orcasgit). Last real release 0.6 on 2019-05-10; Snyk classifies it as **Inactive/discontinued** (no PyPI release in 12+ months). Single key (supports a key *list* for rotation, not per-subject keys). Forks like `django-fernet-fields-v2` (4 stars) and `django-fernet-fields-py-311` exist only to patch Python/Django compatibility. **No per-subject keys, no shredding, no certificate.**
- **django-cryptography** (docs ~2020, 1.1.dev). `EncryptedMixin` wraps a Fernet key; supports an optional per-field `key` argument and a `ttl` (time-to-live) after which the value becomes unreadable — but this is not per-subject keying and not deliberate destruction, and the project is largely dormant. **No per-subject keys, no shredding, no certificate.**
- **django-encrypted-model-fields** (fork of django-cryptographic-fields). Single key from settings (`FIELD_ENCRYPTION_KEY`). **No per-subject keys, no shredding, no certificate.**
- **django-crypto-fields** (erikvw). Uses RSA+AES key *sets* stored in a KEY_PATH folder; designed for de-identification of research datasets (stores hash in the model table, secret in a separate table). "With the RSA keys removed, the dataset is effectively de-identified," which is crypto-shredding-adjacent — but it is a **global** key-set model, not per-data-subject, with no per-subject destruction workflow or certificate. **No per-subject keys, no per-subject shredding, no certificate.**
- **django-pgcrypto-fields / pgcrypto-based packages.** Encryption happens in PostgreSQL via the pgcrypto extension; key passed per query. Single-key model, no per-subject isolation, no destruction, no certificate.
- **encrypt-decrypt-fields** (alpden550) — works for both Django and SQLAlchemy; SHA256+Fernet, single key. **No per-subject keys, no shredding, no certificate.**
- **django-field-cryptography** (incuna, formerly django-simple-aes-field) — Fernet, single `FERNET_KEY`. **No per-subject keys, no shredding, no certificate.**
- **Tink-based or Vault-Transit-based Python ORM field types** — I did **not** find any published, maintained package that binds Google Tink or HashiCorp Vault Transit to a SQLAlchemy `TypeDecorator` or Django `Field` as a per-subject crypto-shredding column type. (Flag: absence of evidence, not proof of absence.)

**Bottom line for §1:** The Python ORM field-encryption ecosystem is entirely single-key (or key-rotation-list) encryption-at-rest. None offers per-subject key isolation, key destruction, or erasure proofs. Your feature combination is not present.

Two Python crypto-shredding projects exist but are **not** ORM-integrated:
- **hupe1980/cryptoshredding** ("Crypto shredding for Python") — real per-key-id shredding (`key_store.delete_main_key(key_id)`) built on the AWS DynamoDB Encryption SDK and KMS. DynamoDB-only, not SQLAlchemy/Django, low-profile.
- **VeritasChain VCP GDPR PoC** (veritaschain/vcp-gdpr-poc) — see §3.

### 2. Granit (.NET / EF Core) status and Python equivalent

**Confirmed and current.** Granit ("granit-fx") is a modular .NET 10 framework, **Apache-2.0 licensed**, marketing itself as "GDPR & ISO 27001 ready out of the box." Its crypto-shredding module is real and matches your description closely:

- Per-entity key isolation via `[Encrypted(KeyIsolation = true)]`; each entity instance gets its own 32-byte AES-256 key stored in **HashiCorp Vault KV v2** (`secret/granit/encryption/isolated/{Entity}/{id}`).
- `ICryptoShredder.ShredAsync` destroys the key in one call; ciphertext becomes noise; audit trail is automatic (`ICryptoShreddingAuditRecorder`).
- **Crucially for your design decision:** Granit's own documentation states that EF Core **value converters receive only a scalar value and have no access to the entity type or ID**, so per-entity key lookup (`{EntityType}:{EntityId}`) is impossible in a value converter. Granit therefore solves it with **two EF Core interceptors** (e.g., `EncryptionIsolationSaveChangesInterceptor`) that iterate the change tracker on write. **This is the direct .NET analogue of your SQLAlchemy "bind_processor only sees the value, not the row" problem — and the vendor's answer was to abandon the type-converter layer and move to a save-interceptor.** Strong signal for your architecture (see §6).

**Maintenance / stars / license / last commit:** I confirmed the **license (Apache-2.0)** and that the project is actively documented and blogging (framework comparisons, SOC 2 mapping, NIS 2 posts) into 2026. I could **NOT** independently confirm exact GitHub star count, last-commit date, or the canonical repository URL — searches surfaced the `granit-fx.dev` site and docs but not a definitively verified GitHub repo (the name collides heavily with IBM "Granite," "Granitic" for Go, "Granular Linux," etc.). **Flag: star count, last-commit date, and repo URL for Granit are UNVERIFIED.** Treat Granit as "actively maintained per its own site as of 2026" but do not cite a specific star/commit figure.

**Python equivalent by same or another author:** None found. No Python port of Granit and no author-linked Python project. This reinforces §1.

### 3. Signed erasure certificate / machine-verifiable proof of erasure

**This is an EMERGING pattern, and in the specific form you propose (an application-layer, per-data-subject signed certificate tied to key destruction in a live database) it is essentially UNCLAIMED in open source — with one recent exception (VeritasChain) aimed at a different domain.**

**(a) Hardware/disk erasure certificates — an ESTABLISHED commercial pattern, but not your use case.** Multiple vendors issue digitally signed, tamper-proof "Certificate of Erasure" documents for wiped drives, tied to NIST 800-88: **Blancco**, **Jetico BCWipe Total WipeOut**, **PIWIPE** (SHA-256 + PKCS#7 signature, QR-verifiable, explicitly marketed for GDPR Article 17), **D-Secure**, **Certus**. These certify *media sanitization* per device/serial number, not per-data-subject field-level erasure inside a running application database. They do not crypto-shred one user's row.

**(b) Application-layer per-subject erasure certificates — EMERGING / essentially unclaimed.** The only project I found issuing a machine-verifiable, signed erasure certificate for per-subject key destruction is **VeritasChain (VCP)**:
- **veritaschain/vcp-gdpr-poc** — "VCP v1.1 Crypto-Shredding PoC," open-sourced (Apache 2.0), announced 2026-01-20. Python implementation with AES-256-GCM, SHA-256 hash chain, and **erasure-certificate generation** (JSON `VCP_ERASURE_CERTIFICATE` with `subject_id_hash`, `keys_destroyed`, `method`, `compliance_references`, `certificate_hash`). VCP v1.2 (2026) formalizes an `ERASURE` event type and an enriched "Erasure Certificate v1" with GDPR Article 17(1) ground reference, KMS key URI, HSM attestation block, `backup_treatment` statement, and optional DPO/CISO co-signers.
- **BUT** VeritasChain targets **append-only audit logs / algorithmic-trading records (MiFID II)**, not a general-purpose ORM write path. It is a blockchain/event-log protocol, not a SQLAlchemy/Django field type. Your capstone's exact framing — signed erasure certificate + hash-chained audit log + per-subject crypto-shredding delivered as a **Python ORM column type / SDK for Postgres** — is not what VeritasChain ships.

Note: VeritasChain's marketing claims "Crypto-shredding is EDPB-endorsed." **That claim is overstated — see §5.** VeritasChain's own later blog (May 2026) more honestly admits "whether crypto-shredding qualifies as 'erasure' under the GDPR is unsettled and jurisdiction-dependent."

**Conclusion:** signed *disk* erasure certs = established; signed *per-subject application-layer* erasure certs = emerging, with VeritasChain the main flag-planter in a different (audit-log/fintech) niche. In the Python ORM niche it is unclaimed.

### 4. Other prior art owning the "crypto-shredding" framing

Beyond Acra, CipherStash, Conduktor, Granit, and VeritasChain (all confirmed), the term and technique are owned across several layers:

**Cloud-vendor key destruction (confirmed; coarse granularity unless you architect otherwise):**
- **AWS KMS** — `ScheduleKeyDeletion`. Per the AWS KMS API Reference: "By default, AWS KMS applies a waiting period of 30 days, but you can specify a waiting period of 7-30 days… Valid Range: Minimum value of 7. Maximum value of 30." And: "Deleting a KMS key is a destructive and potentially dangerous operation. **When a KMS key is deleted, all data that was encrypted under the KMS key is unrecoverable.**" CloudTrail/CloudWatch logs of the deletion serve as proof. Granularity is **per-KMS-key**, not per-row. Community example: `thiagodiogo/aws-kms-rds-crypto-shred` (whole-RDS-instance shredding). `hupe1980/cryptoshredding` uses KMS per-key-id for DynamoDB items.
- **Google Cloud KMS** — distinguishes "Destruction" (irreversibly destroys key material after a destruction period) from "Deletion"; docs explicitly state you "can destroy a key version that was used to encrypt data to crypto-shred data that you want to be permanently unrecoverable." Per-key-version granularity. A Feb 2026 OneUptime guide lays out per-user KEK vs per-record DEK vs per-group key trade-offs on GCP.
- **Azure Key Vault** — used as a KMS backend by Conduktor/Granit; same per-key granularity model. (Flag: I did not separately fetch Azure's key-destruction docs; it is referenced as a KMS option by multiple tools.)

**Key point on granularity:** Native cloud KMS crypto-shredding operates at **whole-key** granularity (which, without extra architecture, tends to mean whole-database, whole-volume, or whole-tenant). Row/field granularity requires the envelope-encryption + per-subject-DEK design you are building — which is precisely why per-subject crypto-shredding is a real engineering contribution rather than a KMS feature call.

**Other framing-owners:**
- **everest-engineering/axon-crypto-shredding-extension** (Java/Axon) — per-subject key isolation for event-sourced systems via `@EncryptedField` + `@EncryptionKeyIdentifier`; "an event that contains the PII of two subjects [can] be encrypted using different encryption keys owned by the respective subjects"; `deleteSecretKey` shreds. The closest conceptual cousin, but Java/Axon event-log, not a Python ORM.
- **CipherStash** (Postgres, "Data Level Access Control," unique key per value via ZeroKMS, TypeScript/Drizzle/Supabase SDKs, cryptographic audit trails) — per-value keys and identity-bound keys, but the marketed workflow is queryable encryption and access control, not per-subject destruction certificates; TypeScript-first, commercial.
- **Acra (Cossack Labs)** — field-level encryption, unique per-field keys, but no per-subject shredding/certificate framing.
- **Apple** ("Erase all content and settings" via effaceable storage) — the canonical device-level example.

No other project owns the specific *Python ORM + per-subject + certificate* framing.

### 5. Regulatory position: does crypto-shredding legally satisfy an erasure obligation?

**Word your central claim carefully. Crypto-shredding is legally UNSETTLED and only conditionally tolerated by EU/India data-protection regulators — it is NOT officially endorsed as legally equivalent to erasure. It is, separately, a recognized *technical* sanitization method under NIST.** This is the single most important caveat in the report, because your project's headline claim depends on it.

- **EDPB Guidelines 02/2025 on blockchain** (v1 adopted 8 April 2025; **v2.0 adopted 7 July 2026**). The EDPB treats key deletion as making data "unintelligible" but pointedly states that **"encrypted personal data is still personal data and encryption does not remove the need for GDPR compliance"** (para 51, v2.0) and warns **"even state-of-the-art encryption perfectly implemented will be overtaken by time if the blockchain is retained indefinitely."** Erasure compliance is framed as rendering data **"effectively anonymous"** — requiring that on-chain data not allow direct identification AND that re-identifying off-chain data be erased (para 103). The EDPB also states **"technical impossibility cannot be invoked to justify non-compliance"** (para 50) and that it is "not advisable to register personal data" on-chain at all (para 104). Notably, industry commenters (GBBC, Bitkom) explicitly *asked* the EDPB to state that key destruction fulfils the right to erasure — and the EDPB **declined** to adopt that categorical language. So key destruction is a *tolerated technique within a broader anonymisation strategy*, not a standalone legal equivalence.
- **EDPB Guidelines 01/2025 on Pseudonymisation** (adopted 16 January 2025; still in draft/consultation as of the research date — flag). Core doctrine: pseudonymised data **remains personal data** while anyone retains the means to re-identify; deleting the additional information (the "key") does **not** automatically make data anonymous — the (irreversible) conditions of anonymisation must be met. This cuts directly against a strong "delete the key = erased" claim. The area is in flux post **CJEU C-413/23 P (EDPS v SRB)** (AG opinion 5 Feb 2025 takes a more relative, risk-based view); the EDPB held a stakeholder event on 12 December 2025 to reconsider.
- **National DPA decisions:** **None found** squarely ruling on crypto-shredding-as-erasure. The most relevant regulator artifact is the **Spanish AEPD's technical proof-of-concept** on blockchain and the right to erasure (cited by the EDPB), which explored chain redaction/governance, not a legal ruling that key destruction alone equals erasure. **Flag: legally unadjudicated.**
- **ENISA:** **No** ENISA publication found that endorses crypto-shredding as an erasure mechanism. ENISA's relevant work (Pseudonymisation techniques, 2019; Advanced Techniques & Use Cases, 2021) treats encryption/keys as *pseudonymisation* (reversible; data stays personal) — again cutting against the strong claim.
- **NIST SP 800-88 Rev. 2** — **finalized 26 September 2025.** Per NIST's publication record: "Date Published: September 2025," "Document History: 09/26/25: SP 800-88 Rev. 2 (Final)," "Supersedes: SP 800-88 Rev. 1 (12/17/2014)," authored by Ramaswamy Chandramouli (NIST) and Eric Hibbard (Samsung Semiconductor), DOI 10.6028/NIST.SP.800-88r2. "Cryptographic Erase (CE)" is a **Purge-level** sanitization technique elevated to its **own dedicated Section 3.2** (with subsections 3.2.1 Strength of Cryptography for CE, 3.2.2 Applicability, 3.2.3 Sanitization of Keys, 3.2.4 Quality of Implementations, 3.2.5 Traceability). Rev. 2 defers most technique detail to IEEE 2883-2022 but retains explicit CE guidance and strengthened its prerequisites (drive encrypted from first use; validated encryption; verifiable key destruction; traceability). **Important:** this is a US *technical* media-sanitization standard, not a GDPR/DPDP legal instrument — it validates CE as technically sound, not as legally-sufficient erasure under EU/India law.
- **India DPDP Act 2023 / DPDP Rules 2025 (notified November 2025):** Rule 8 requires **"erasure"** generically (with a 48-hour advance notice to the Data Principal before scheduled erasure, and Third-Schedule retention timelines, e.g., 3 years for large e-commerce/gaming/social-media platforms). **No rule names cryptographic erasure or key destruction as an accepted method.** Encryption appears only in **Rule 6** (reasonable security safeguards: "encryption, obfuscation, masking or virtual tokens"), not as a substitute for erasure. So India is **silent/generic** on whether crypto-shredding qualifies.

**How strongly can you word the claim?** Safe: "Crypto-shredding is a recognized *technical* method of cryptographic erasure (NIST SP 800-88 Rev. 2, §3.2) and is widely *proposed* as a means of satisfying GDPR Art. 17 / DPDP Rule 8 erasure obligations." **Unsafe / must avoid:** "Crypto-shredding is EDPB-endorsed" or "legally equivalent to erasure" — regulators have expressly declined that equivalence and treat encrypted data as still personal data. Frame your project as implementing a defensible, auditable *technique* whose *legal* sufficiency is jurisdiction-dependent and unsettled.

### 6. Is SQLAlchemy `TypeDecorator` viable here? The sibling-column key-selection risk

**`TypeDecorator` is viable for the encryption transform itself, but it is the WRONG place to select a per-subject key, for exactly the reason you identified. Follow Granit's lead and do key selection in a session/flush event or interceptor, not in `bind_processor`.** This is your key technical risk and the research confirms it is real.

**The core limitation (confirmed from SQLAlchemy docs):** `TypeDecorator.process_bind_param(self, value, dialect)` and `process_result_value(self, value, dialect)` receive **only the scalar value and the dialect** — never the row, the ORM instance, or sibling columns. There is no supported way to reach `subject_id` from inside a type processor. This is identical to the EF Core value-converter limitation that forced Granit to use save-interceptors instead. So a pure-`TypeDecorator` design cannot pick a per-subject key.

**How existing systems solve "I need a sibling column to pick the key":**
1. **`contextvars` (recommended primary pattern).** Set the current subject/tenant key context in a `contextvars.ContextVar` at the start of a request/operation; the `TypeDecorator` reads it inside `process_bind_param`/`process_result_value`. This is the same pattern widely used for SQLAlchemy + Postgres Row-Level Security multi-tenancy (set `app.current_tenant` per request via a ContextVar + event listener). Clean and async/thread-safe, but requires that the subject key be set in context before the flush — natural on a per-request write path, awkward for bulk writes mixing many subjects.
2. **Session events — `before_flush` (recommended for mixed-subject writes).** In `SessionEvents.before_flush`, iterate `session.new` / `session.dirty`, read each instance's `subject_id` directly (full object access), fetch/derive the per-subject DEK, and encrypt into the target column. This is the Python analogue of Granit's `SaveChangesInterceptor` and handles a single flush touching rows of different subjects — which `contextvars` cannot cleanly express.
3. **Mapper persistence events (`before_insert`/`before_update`).** Give per-object access (mapper, connection, target), but SQLAlchemy docs warn these run **after the flush plan is decided**: you may only change attributes "local to the object's row" and must not alter session state. Encrypting the row's own column is allowed; anything else is unsafe. Usable but more constrained than `before_flush`.
4. **Composite types / `@hybrid_property`** wrapping value+key — possible but leaks the pattern into every model and defeats the "one line per column" goal.

**Documented `TypeDecorator` pitfalls to plan for:**
- **Result processors run on NULLs and on outer-join non-matches.** SQLAlchemy discussion #8970 documents that with `LEFT OUTER JOIN`, `process_result_value` is invoked even when there are no rows of that model (columns come back NULL). Your `process_result_value` must handle `None` and already-shredded (undecryptable) values gracefully — return `None`/sentinel rather than raising. This matters directly after shredding: reads of a shredded subject's columns must not crash `session.query(...).all()`.
- **Bulk operations bypass the ORM flush.** `Session.bulk_insert_mappings`/`bulk_update_mappings` and Core `insert()`/`update()` do **not** run `before_flush` (Core statements may bypass ORM events entirely). If you put key selection in `before_flush`, bulk paths silently skip encryption. Document that protected models must not use bulk ORM shortcuts, or add Core-level `before_execute` handling. (Flag: the bulk-bypass warning is derived from SQLAlchemy's documented event model — which is reliable — rather than from a single blog enumerating every case.)
- **Querying/filtering on encrypted columns.** Because ciphertext differs per value (and per subject), you cannot do server-side `WHERE encrypted_col = ?`, `LIKE`, ordering, or unique constraints on the plaintext. sqlalchemy-utils users hit exactly this (open issues on `like`/`ilike` and unique constraints). Plan blind-index columns if you need lookups.
- **Alembic migrations to BYTEA/JSONB.** Changing an existing column to your encrypted type means an Alembic column-type migration (e.g., to `BYTEA`/`LargeBinary` or `JSONB`) plus a data-migration pass to encrypt existing rows; Alembic autogenerate often does not detect `TypeDecorator` changes cleanly, so you will hand-write these. (Flag: a well-known Alembic behavior for custom types; not separately fetched this session.)
- **`InvalidPaddingError` on decrypt with the wrong key** — sqlalchemy-utils issue #771 (Jan 2025) shows what happens on key/data mismatch. For you this is a feature (post-shred reads fail), but you must catch it and convert to a clean "erased" sentinel rather than a 500 error.

**Recommended architecture (synthesized):** Keep a thin `TypeDecorator` (or Django `Field`) purely for the storage transform and to mark a column as protected, but perform **per-subject key resolution and encryption in a `before_flush` session event** (mirroring Granit's interceptor), with a **`contextvars`** fast-path for single-subject request scopes. Make `process_result_value` null-safe and shred-safe. This gives you the "one line per column" developer ergonomics on the model while putting the row-aware logic where it can actually see `subject_id`.

## Recommendations

1. **Proceed — the gap is real.** Build it, and position the novelty precisely: "the first open-source **Python ORM-integrated** per-data-subject crypto-shredding gateway with signed erasure certificates." Do not claim novelty of crypto-shredding itself (owned by Acra/CipherStash/Conduktor/Granit/VeritasChain/cloud KMS) or of erasure certificates for disks (Blancco/Jetico/PIWIPE). Claim the *combination + Python-ORM ergonomics*.
2. **Adopt the interceptor/event architecture now, not `TypeDecorator`-only.** The single biggest design error would be selecting the per-subject key inside `bind_processor`. Granit already proved (in .NET) that the type-converter layer cannot see the entity ID and that a save-interceptor is required. Use `before_flush` + `contextvars` in Python.
3. **Word the legal claim defensively.** Cite NIST SP 800-88 Rev. 2 §3.2 for the technical legitimacy of cryptographic erase, and describe GDPR Art. 17 / DPDP Rule 8 sufficiency as *argued/emerging and jurisdiction-dependent*. Explicitly cite the EDPB's position that encrypted data remains personal data. Do NOT repeat VeritasChain's "EDPB-endorsed" claim.
4. **Differentiate from Granit and VeritasChain in your literature review.** Granit = .NET/EF Core; VeritasChain = append-only audit-log/fintech protocol. Neither is a Python ORM column type + SDK for Postgres. Make this explicit — it is your defensibility.
5. **Handle the known `TypeDecorator` pitfalls up front** as test cases: null/outer-join reads, post-shred reads (catch `InvalidPaddingError` → sentinel), bulk-operation bypass, blind-index for lookups, and Alembic hand-written migrations. Demonstrating these is exactly the engineering depth that shows the gap is non-trivial.

**Benchmarks / thresholds that would change these recommendations:**
- If a maintained PyPI package appears combining per-subject keys + shredding + ORM column type, re-scope to differentiate on certificates/audit-log. (None exists today.)
- If the EDPB issues final guidance (or a DPA issues a decision) explicitly accepting key destruction as Art. 17 erasure, you may strengthen the legal claim from "argued" to "recognized." Watch the post-C-413/23 P anonymisation guidance.
