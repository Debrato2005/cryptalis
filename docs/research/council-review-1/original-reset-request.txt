# 0. Core outcome

Cryptalis should become:

> **A manifest-driven application data-protection layer that can be added to an existing backend with minimal backend changes, encrypts selected sensitive data before PostgreSQL sees it, preserves explicitly supported queries over encrypted data, manages the entire key/data lifecycle, fails closed, and can be safely rolled back or completely removed.**

The primary product property is **usability**.

A normal developer should not need to become a cryptographer.

The intended mental model is approximately:

```text
existing backend
      +
cryptalis manifest
      +
minimal integration
      ↓
normal application behaviour
      ↓
encrypted sensitive database fields
      +
declared encrypted search
      +
managed keys/lifecycle
```

Complex internals are allowed.

Complex public UX is not.

# 8. Public-source threat model

# 10. P0 failures — architecture must solve these

Treat these as product-killing risks.

## Bypass paths

Raw SQL, `COPY`, Core/bulk operations, ETL, alternate workers and migrations must not silently persist plaintext into supposedly protected storage.

Research how to enforce or detect this without destroying usability.

Consider:

- ORM interception;
- physical schema design;
- DB permissions;
- private physical columns;
- constraints/framing checks;
- proxy enforcement;
- writer registration;
- static/runtime doctor checks.

Do not claim universal prevention if the mechanism only detects some paths.

Unknown coverage must remain `UNKNOWN`, never `PASS`.

## Silent fallback

Unsupported encrypted queries must never:

- become plaintext queries;
- silently skip encryption;
- silently return incomplete results;
- silently change semantics.

Use typed failures such as:

```text
UnsupportedEncryptedQuery
```

or equivalent.

Default deny.

## Ciphertext relocation

Authenticated encryption alone is insufficient if ciphertext can be copied between valid locations.

Research and define exact authenticated context.

Likely candidates include stable identifiers for:

```text
protection domain
tenant
subject if applicable
record identity
model/table logical identity
field logical identity
representation
format
key generation
purpose
```

Do not bind long-term ciphertext only to mutable SQL names if table/column renames must remain possible.

## Replay/freshness

AEAD authenticity does not establish freshness.

Decide exactly which replay threats Cryptalis prevents and which it does not.

Do not casually build an enormous freshness service unless the threat justifies it.

Choose the simplest mechanism consistent with the declared protection.

## Nonce/RNG safety

Research and select the exact approved primitive/composition.

Compare current vetted options and libraries.

Do not invent cryptography.

Address:

```text
nonce generation
multi-process workers
fork
multiple hosts
RNG failure
key/nonce limits
key commitment if the actual threat model requires it
format authentication
```

The architecture must contain one clear answer, not several candidate algorithms.

## Key authority

Resolve:

```text
where root authority lives
provider identity
secret-zero bootstrap
workload authentication
least privilege
key scope
provider outage
audit
cache boundaries
revocation
```

Long-lived raw root keys in application `.env` are not an acceptable production design.

Prefer cloud workload identity / Vault authentication / equivalent mechanisms where applicable.

## Rotation

Explicitly distinguish:

```text
KEK/wrapper rewrap
payload encryption-key generation change
search-index key rotation/reindex
```

Do not treat these as the same operation.

Design rolling-deploy compatibility:

```text
read new generation
→ change writer generation
→ migrate existing data
→ verify coverage
→ retire old generation only when safe
```

## Migration safety

Protection migrations must be:

```text
resumable
idempotent
bounded
observable
crash-safe
concurrency-aware
fully verified
```

Investigate shadow representations and safe cutover.

Define the exact irreversible boundary.

Do not report a partial migration as success.

## Residual plaintext

Protecting current rows does not erase historical plaintext from:

```text
WAL
dead tuples
TOAST
replicas
snapshots
backups
exports
```

Design truthful reporting.

Do not make impossible sanitization claims.

## Rollback

Easy rollback is a core product requirement.

Define what rollback means before and after irreversible cleanup.

Prefer keeping a verified rollback representation until the user crosses an explicit contraction/finalization boundary.

After destructive cleanup, do not pretend rollback remains cheap.

## Restore

A restored old database must not automatically restore old authority.

Research and define the smallest external non-restored state necessary to prevent:

```text
revoked keys becoming valid
deleted subjects becoming recoverable
old policy becoming authoritative
completed destructive operations being forgotten
```

## Removal / uninstall

Cryptalis must not create vendor lock-in.

Design a complete:

```text
protected → plaintext → Cryptalis-independent
```

workflow.

It must:

- backfill plaintext safely;
- verify every required value;
- switch the application;
- prove the application works without Cryptalis;
- inventory old encrypted backups and required readers/keys;
- retire search metadata;
- retire protected columns;
- retire eligible keys only when safe;
- remove Cryptalis metadata;
- remove the package last.

Do not equate package uninstall with secure decommissioning.

## Crypto-shredding

Resolve the exact scope and claim.

Differentiate:

```text
access revoked
key material no longer used for new operations
provider deletion requested
provider deletion pending
recovery still possible
bounded destruction verified
```

Never print `ERASED` because one local row was deleted.

Research NIST SP 800-88 Rev. 2 and provider-specific deletion semantics.

Consider restore-resistant tombstones.

Resolve the interaction between:

```text
per-subject shredding
shared search indexes
backup recoverability
key granularity
```

## Search-token/ciphertext consistency

Payload ciphertext and its searchable representation must never drift.

Define atomic update semantics and consistency verification.

## Supply-chain security

Cryptalis itself handles plaintext and keys, so package compromise is catastrophic.

Research current 2026 Python/PyPI supply-chain incidents before making claims.

Define a proportionate release policy covering:

```text
maintainer authentication
protected release environment
minimal dependencies
hash locking
SBOM
artifact signing/provenance
reproducible builds where practical
install/import-time behaviour
security disclosure
critical format flaw response
```

Do not build custom supply-chain tooling if mature tools already exist.

> **Secure defaults beat configurability.**
