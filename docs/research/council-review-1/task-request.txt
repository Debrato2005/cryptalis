2. FIX THE COUNCIL FINDINGS (each needs: protocol/spec in its canonical owner doc, invariants,
   failure table, an adversarial test scenario in the build guide, and a ledger entry)
------------------------------------------------------------------
HIGH
H1. Admission/fence ordering and ownership after lock loss. Specify the exact order of
    admission check, fence/lease token, database commit and every irreversible external effect.
    Define what a stale or ex-owner process may and may not do, and how that is enforced
    (token checked at the authority or the DB, not just in the process). Define behaviour when
    the lock/lease is lost mid-operation.
H2. Durable evidence for ordinary commit reconciliation. Handle the ambiguous commit
    (connection drops after COMMIT is sent): how does Cryptalis learn whether the DB commit
    happened relative to external receipts/effects? Design the evidence record (for example
    written in the same DB transaction), idempotency keys, and the reconcile procedure.
H3. ORM state preservation and atomic publication through public APIs. Define what happens to
    the identity map, attribute expiry/refresh, merge, deferred loads, hybrid/column
    properties, and how payload plus search terms are published atomically. Use only public,
    documented SQLAlchemy extension points on the pinned version. If that cannot be done
    safely, shrink the supported surface and say so.
H4. Async preparation when flush callbacks add protected writes. Cascades, events and defaults
    can create protected writes during flush, when async I/O is not allowed. Define the
    pre-flush preparation phase, how late additions are detected, and fail closed on them.
FURTHER
M5. Predicate errors: fix the exact admitted predicate grammar (NULL, negation, OR, empty IN,
    case-insensitive, casts, joins). Everything else raises a typed error, never wrong results.
M6. Quota and rollback capacity: rollback mirrors, extra columns/indexes, KMS/DynamoDB/S3
    quotas and throttling. Add a preflight capacity check and defined behaviour on exhaustion
    mid-transition.
M7. Uniqueness limits: scope (tenant, soft delete, multi-column, partial indexes), concurrent
    insert races, what the conflict leaks, and what is unsupported by design.
M8. Recovery commands: a catalogue of stuck states and the operator command for each
    (resume, abort, reconcile, break-glass). Each must be idempotent and must never publish
    plaintext. Include them in tests.
M9. Subject-denial naming: the word "shred" overclaims. Rename the command, output strings
    and docs to reflect managed denial; keep domain destruction distinct. Keep claims
    consistent everywhere.
M10. Adoption wording: rewrite README and claims to state the real adoption cost (stack
    scope, AWS dependency, operational prerequisites). Remove any "simple/transparent/zero
    change" wording the design cannot support.

A1. Control-plane weight. The design requires AWS KMS + DynamoDB + S3 receipts. Evaluate it

    complexity, lock-in, minimum viable footprint. Consider whether external state can be
    collapsed or abstracted behind a small provider interface with a clearly non-production

A4. Blocked-decision triage. Of the decisions marked DECIDED-BLOCKED-ON-TEST, mark which

A5. Re-run the product kill list (every item) against the current docs. Record pass/fail with
