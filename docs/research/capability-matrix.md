# Competitive capability matrix

Updated 2026-10-23. This is a living research record, not a specification,
compatibility admission, security audit, or reproduced vendor benchmark.
The target is **one comprehensive, production-grade first public release**.
All [34 objectives](../BUILD_CHECKLIST.md#objective-ledger) and the complete SRS
remain in scope. Internal milestones do not reduce that target. A refusal
protects the current runtime. It does not complete a requested capability.

[Status](../status.md) owns executable claims. [Compatibility](../compatibility.md)
owns current admission. [security](../security.md) owns threat/leakage requirements;
[decisions](../decisions.md) owns architecture changes. All seven production gates
remain UNKNOWN. Competitor features are published contracts unless explicitly
identified as inspected source. No competitor was installed, executed, tested,
or independently audited in this research pass.

## Immediate engineering choices supported by the evidence

1. Complete the coherent pre-adoption Doctor and independent-application lifecycle
   journey first as an **internal integration milestone**. This does not defer
   advanced capabilities from the first public release. Reuse current attach,
   diagnostics, maintenance and artifact tooling.
2. Resolve typed scalar/range and exact bounded string-search profiles as separate
   architecture decisions. Mature searchable constructions exist, but their
   leakage, codec, platform and result contracts differ. MongoDB's bounded exact
   string surface is useful evidence. CipherStash's fuzzy surface is a distinct
   product operation. Neither licenses a generic LIKE rewrite or a new cipher.
3. Design online migration around complete writer coverage and atomic changes.
   Keep the current verified maintenance path while the online path is developed
   and qualified. Do not mistake retained-plaintext rollback for latest-data exit.
4. Prepare real provider and independent review work in parallel. Preserve generic
   custody interfaces and truthful external blockers. Do not build a replacement
   KMS/control plane merely to imitate ZeroKMS's implementation.

The acceptance unit is the original application's working journey: install,
manifest, Doctor, plan/apply, independent persistence check, normal CRUD and
admitted searches, tenant/concurrency behavior, expiry/wrong-key/corruption
refusal, each rotation, interruption/resume, fresh-cluster backup/restore,
latest-data reversal, complete removal, and package-free native restart with
values and relevant schema semantics compared to baseline. Add deterministic
fault injection only where ordinary application actions cannot establish the
critical invariant. A partial journey remains partial.
